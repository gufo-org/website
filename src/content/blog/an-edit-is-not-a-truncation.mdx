Editing an earlier message in a chat feels like a small change. You fix one sentence near the end of a long conversation, and almost every token before it is the same. On a pure-attention model, the server could keep the KV rows for the matching prefix, drop the rest and carry on.

Gufo's hybrid models can't do that. Next to the KV memory, they carry **recurrent state**: a fixed-size summary of everything read so far. It only moves forward. Once it has absorbed token 8,192, there is no way to wind it back to token 7,000.

## Exact restore points

So the cache redesign doesn't try to cut state back. It keeps **checkpoints**: frozen copies of the recurrent state at exact token positions, plus the KV rows up to that point. When an edited prompt arrives, Gufo restores the latest checkpoint that is still an exact prefix of it and prefills the rest.

Step through the figure below. In step 2 the edit lands after token 7,000. The request still matches 7,000 tokens of history, but the nearest usable checkpoint is at 6,144, so the amber stretch is recomputed even though those tokens didn't change.

<CacheFigure scenario="edit" steps="1-4" figure={1} caption="Editing token 7,001 restores the checkpoint at 6,144, not 7,000: matching tokens alone aren't a usable state." />

Two details in that figure are worth a second look:

1. **Extra checkpoints are cheap.** A@4096, A@6144 and A@8192 share their full 2,048-token chunks, so each extra boundary mostly costs its fixed state. Compare the RAM total with the "unshared" figure next to it.
2. **The edited branch has its own provenance.** After step 3, the first three chunks still come from A, but the fourth was computed on the new branch. It gets a new colour, even where it covers tokens that didn't change.

## When the boundary is learned

Edits are unpredictable, so the best the cache can do is keep restore points dense enough. Subagents are different: they all share the parent's system prompt and tools, then diverge at the same place every time. The first subagent pays for the gap once and saves a checkpoint exactly where the histories split. Every later one restores it directly.

<CacheFigure scenario="fork" step={3} figure={2} caption="The second subagent restores the learned 6,000-token boundary and prefills only its own task." />

## What this means in practice

- Editing a message near the end of a long conversation costs, at most, the gap back to the previous checkpoint. It doesn't cost the whole conversation.
- Denser checkpoints shrink that gap, at the price of fixed state per checkpoint. The memory section of the [cache explorer](/cache) lets you try different numbers.
- Agent workloads that fork from a shared prefix get exact restore points for free after the first request.

The redesign is being built and isn't switched on yet. The figures use the same made-up conversations as the cache explorer, and the RAM numbers are estimates from measured sizes, not benchmarks.
